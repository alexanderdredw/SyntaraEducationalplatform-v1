## 0. Кратко

**Battle** — живая викторина для класса, похожая на Kahoot:
1. Учитель собирает **Battle-тест**: вопросы с вариантами ответов и временем на вопрос.
2. Учитель запускает **игровую сессию**, и система выдаёт код вида `KTR583`.
3. Ученики вводят код у себя в кабинете и попадают в **лобби**.
4. Учитель видит участников и нажимает «Начать».
5. Все одновременно отвечают на каждый вопрос на время. Сервер проверяет ответы и синхронизирует экраны.
6. В конце формируется **рейтинг**: сначала по числу правильных ответов, при равенстве — по скорости. Первые три места показываются на **пьедестале** (золото, серебро, бронза), остальные — в таблице.
7. Результаты и история сохраняются.

Интерфейсы разные: у учителя экран ведущего (подходит для проектора), у ученика «пульт» для ответов.

## 1. Как это ложится на текущую архитектуру

Что уже есть в проекте и что переиспользуем:

| Есть в проекте | Как используем в Battle |
|---|---|
| NestJS API, модульный монолит (`apps/api/src/modules/*`) | Новый модуль `modules/battle` |
| Сессии по cookie `sid`, CSRF, guards по ролям, RLS | Та же авторизация для всех операций Battle и потока событий |
| SSE-потоки (`text/event-stream`) в модуле ИИ; nginx `/api/` с `proxy_buffering off` | Транспорт «сервер → клиент» для живых событий игры |
| Redis 7 (`ioredis`), rate-limit на Redis | Pub/Sub для рассылки событий между экземплярами API, счётчики, блокировки |
| Worker на BullMQ (`apps/worker/src/queues.ts`) | Отложенные задачи-«таймеры» закрытия вопроса и автоперехода |
| Drizzle + PostgreSQL 16, миграции SQL | Новые таблицы `battle_*`, они же источник истины результатов |
| Модель вопросов квизов (`questions`, `answer_options`, один правильный вариант — BR-QZ-02) | Тот же принцип вариантов; импорт вопросов из квизов тем |
| Классы и членство (`classes`, membership) | Ограничение «кто может войти в сессию» |
| Дизайн-токены и компоненты `packages/ui` | Все экраны Battle только из них, плюс новые токены медалей |
| i18n RU/KK/EN, `needs_confirmation.json` | Все тексты интерфейса Battle |

### 1.1 Выбор транспорта реального времени

**Решение: SSE (сервер → клиент) + обычные POST-запросы (клиент → сервер) + Redis Pub/Sub.**

Почему не WebSocket (Socket.IO):
- SSE уже работает в проекте через nginx и cookie-сессию: не нужны новая библиотека, настройка `Upgrade` в nginx и отдельная авторизация сокета.
- Ответ ученика — редкое действие (раз в 5–60 с), поэтому POST с идемпотентным ключом надёжнее и проще, чем сообщение в сокете. К нему применимы уже существующие CSRF, rate-limit и валидация Zod.
- SSE сам переподключается и передаёт `Last-Event-ID`. На слабом интернете это устойчивее.
- Задержка доставки события через Redis Pub/Sub и SSE — десятки и сотни миллисекунд, для викторины этого достаточно.

WebSocket остаётся запасным вариантом: если нагрузочный тест (этап B6) покажет, что SSE не справляется, транспорт меняется только в слое `BattleRealtimeGateway`. Поэтому весь код событий изолируется за интерфейсом (раздел 6.4).

### 1.2 Источник истины и масштабирование

- **PostgreSQL — источник истины.** Он хранит состояние сессии (статус, номер вопроса, время начала, дедлайн), участников, каждый ответ и итоги.
- **Redis** отвечает за рассылку событий (`battle:{sessionId}`), быстрые счётчики «ответили X из Y», блокировки переходов и дедупликацию.
- **API без состояния.** Ученики одной игры могут быть подключены к разным экземплярам API, события доходят до всех через Pub/Sub. Перезапуск API не ломает игру: клиенты переподключаются и получают снимок из PostgreSQL.
- **Время только серверное.** Время ответа считается на сервере от момента начала вопроса до получения ответа.

## 2. Механика игры

### 2.1 Battle-тест (шаблон)

- Владелец — учитель. Тест виден и доступен только ему.
- Поля: название (≤ 120 символов), описание (необязательно, ≤ 500), язык содержания (RU/KK/EN — на нём учитель пишет вопросы; перевода нет).
- Вопросов от 1 до 50.
- Вопрос:
  - текст ≤ 300 символов, необязательная картинка (только из нашего хранилища, проверка как у обложек BR-FILE-01);
  - тип `single_choice` (2–4 варианта, ровно один правильный) или `true_false` (варианты «Верно» / «Неверно»);
  - время на ответ: 5, 10, 20 (по умолчанию), 30, 60 или 90 с.
- Вписанный ответ (`text_input`) в Battle **не поддерживается**: в живой игре он медленный и спорный при проверке.
- **Импорт:** учитель может скопировать вопросы из квиза своей темы или базовой темы платформы, только типы `single_choice` и `true_false`. Вопросы копируются: изменения в Battle-тесте не затрагивают исходный квиз.
- Тест можно дублировать и архивировать. Удаление теста с прошедшими сессиями запрещено, только архив.

### 2.2 Игровая сессия

- Запускается из теста. Учитель выбирает **класс** и настройки (раздел 2.5).
- При запуске в сессию **замораживается снимок** вопросов (`questions_snapshot`). Правка теста после запуска не влияет ни на идущую игру, ни на историю.
- Одновременно у учителя может быть не больше 3 активных сессий (не `finished` и не `cancelled`).

### 2.3 Код сессии (BR-BTL-01)

- Формат: 3 заглавные латинские буквы A–Z и затем 3 цифры 1–9, например `KTR583`. Регулярное выражение: `^[A-Z]{3}[1-9]{3}$`.
- Генерация криптостойкая (`crypto.randomInt`). Код уникален среди **активных** сессий (`lobby`, `in_progress`); после завершения или отмены он освобождается. При коллизии — до 10 повторов, затем ошибка 503.
- Ввод не зависит от регистра и пробелов: `ktr 583` → `KTR583`.
- Код хранится в открытом виде (он короткоживущий и показывается на проекторе). Уникальность проверяется частичным индексом `UNIQUE (code) WHERE status IN ('lobby','in_progress')`.
- Срок жизни: лобби без старта закрывается через 60 минут, игра без активности — через 30 минут (статус `cancelled`, причина `expired`).
- Защита от перебора: не больше 10 попыток ввода кода за 10 минут на ученика и 30 на IP (существующий rate-limit). Ответ «код не найден» одинаковый для несуществующего и чужого кода.

### 2.4 Автомат состояний (SM-BTL)

```
lobby ──start──▶ question ──(дедлайн | все ответили | учитель «Завершить вопрос»)──▶ reveal
reveal ──(учитель «Далее» | авто через N с)──▶ leaderboard ──next──▶ question (i+1)
reveal/leaderboard на последнем вопросе ──next──▶ finished
любое состояние ──учитель «Завершить игру»──▶ finished (досрочно, итог по отвеченным вопросам)
lobby ──учитель «Отменить» | истечение──▶ cancelled
```

- Каждый переход — одна транзакция PostgreSQL с `SELECT … FOR UPDATE` строки сессии и проверкой ожидаемого состояния и номера вопроса. Повторный или запоздавший переход ничего не меняет (идемпотентность).
- Каждое изменение увеличивает `state_version`. Все события несут `version`, и клиент игнорирует события со старой версией.
- `leaderboard` (промежуточный рейтинг, топ-5) показывается после каждого вопроса, кроме последнего, если включена настройка; иначе после `reveal` сразу следующий вопрос.

### 2.5 Настройки сессии

| Настройка | По умолчанию | Описание |
|---|---|---|
| Класс | обязательно | Войти могут только активные участники класса (BR-BTL-02) — ⚠ см. вопрос 1 |
| Перемешать вопросы | выкл | Один порядок для всех участников |
| Перемешать варианты | выкл | Один порядок для всех; цвета и фигуры привязаны к позиции |
| Промежуточный рейтинг | вкл | Топ-5 после каждого вопроса |
| Автопереход | выкл | После `reveal` через 5 с, после `leaderboard` через 5 с переход без нажатия |
| Позднее подключение | выкл | Разрешить вход после старта; пропущенные вопросы засчитываются как без ответа |
| Максимум участников | 100 | Лимит сессии (BR-BTL-08) |

### 2.6 Ответы (BR-BTL-03)

- Ученик отвечает **один раз** на вопрос, изменить ответ нельзя.
- Принимается ответ, пришедший на сервер не позже `deadline_at + 500 мс` (запас на сеть). Более поздний отклоняется с ошибкой 409 `questionClosed`.
- Время ответа `response_ms = answered_at − question_started_at`, где оба момента — серверные.
- Повторная отправка с тем же `clientAnswerId` возвращает уже сохранённый результат (идемпотентность). Другой вариант на тот же вопрос — 409 `alreadyAnswered`.
- **Правильность до раскрытия не сообщается** ни ученику, ни в сетевых ответах. Ученик видит только «Ответ принят».
- Вопрос закрывается досрочно, когда ответили все активные (не выгнанные и подключённые за последние 30 с) участники.

### 2.7 Рейтинг (BR-BTL-04)

Порядок сортировки участников:
1. `correct_count` — по убыванию;
2. `correct_time_ms` — сумма `response_ms` **правильных** ответов, по возрастанию (кто быстрее отвечал правильно);
3. при полном равенстве обоих — **одно и то же место** (например, два вторых места, затем четвёртое).

- Выгнанные участники в рейтинг не входят. Вышедшие сами остаются с набранным результатом.
- Итоги (`final_rank`, `correct_count`, `correct_time_ms`, `answered_count`) записываются в `battle_participants` при переходе в `finished`. Пересчёт по `battle_answers` даёт тот же результат (тест).
- Пьедестал — места 1–3 (с учётом совпадающих мест, пьедестал может содержать больше трёх человек). Остальные участники — в таблице.

### 2.8 Участники

- Отображаемое имя — имя ученика из профиля и первая буква фамилии («Асель К.»). Свои ники не вводятся: так защищаем детей от неподобающих имён. ⚠ вопрос 7.
- Учитель может **выгнать** участника (в лобби или в игре). Выгнанный не может вернуться в эту сессию.
- Обрыв связи — это не выход: ученик возвращается тем же аккаунтом и продолжает со следующего события.
- Ученик может нажать «Выйти из игры». Повторный вход по коду возможен, пока сессия активна.

### 2.9 Очки опыта (XP)

По умолчанию Battle **не начисляет XP** и не влияет на освоение тем, «Мои показатели» и аналитику класса, чтобы не искажать учебные метрики. ⚠ вопрос 4.

## 3. Модель данных (миграция `0007_battle.sql` + схема Drizzle `packages/db/src/schema/battle.ts`)

```
battle_quizzes
  id uuid PK, owner_id uuid FK users NOT NULL, title text NOT NULL (≤120),
  description text (≤500), locale locale NOT NULL, archived_at timestamptz,
  created_at, updated_at

battle_questions
  id uuid PK, battle_quiz_id uuid FK NOT NULL, position int NOT NULL,
  type question_type NOT NULL CHECK (type IN ('single_choice','true_false')),
  text text NOT NULL (≤300), image_media_id uuid FK media_files NULL,
  time_limit_sec int NOT NULL CHECK (time_limit_sec IN (5,10,20,30,60,90)),
  source_question_id uuid NULL (если импортирован), archived_at, created_at, updated_at
  UNIQUE (battle_quiz_id, position) DEFERRABLE

battle_options
  id uuid PK, battle_question_id uuid FK NOT NULL, position int NOT NULL (1..4),
  text text NOT NULL (≤150), is_correct boolean NOT NULL DEFAULT false
  UNIQUE (battle_question_id, position); UNIQUE (battle_question_id) WHERE is_correct

battle_session_status: enum ('lobby','in_progress','finished','cancelled')
battle_phase: enum ('lobby','question','reveal','leaderboard','finished')

battle_sessions
  id uuid PK, battle_quiz_id uuid FK NOT NULL, host_id uuid FK users NOT NULL,
  class_id uuid FK classes NOT NULL, code char(6) NOT NULL CHECK (code ~ '^[A-Z]{3}[1-9]{3}$'),
  status battle_session_status NOT NULL, phase battle_phase NOT NULL,
  settings jsonb NOT NULL, questions_snapshot jsonb NOT NULL,
  current_index int NULL, question_started_at timestamptz NULL, deadline_at timestamptz NULL,
  state_version int NOT NULL DEFAULT 0, cancel_reason text NULL,
  created_at, started_at, finished_at, last_activity_at
  UNIQUE INDEX ux_battle_active_code ON (code) WHERE status IN ('lobby','in_progress')
  INDEX (host_id, created_at DESC)

battle_participants
  id uuid PK, session_id uuid FK NOT NULL, student_id uuid FK users NOT NULL,
  display_name text NOT NULL, joined_at, left_at NULL, kicked_at NULL, last_seen_at,
  correct_count int, answered_count int, correct_time_ms int, final_rank int
  UNIQUE (session_id, student_id)

battle_answers
  id uuid PK, session_id uuid FK NOT NULL, participant_id uuid FK NOT NULL,
  question_index int NOT NULL, option_position int NOT NULL, is_correct boolean NOT NULL,
  response_ms int NOT NULL CHECK (response_ms >= 0), answered_at timestamptz NOT NULL,
  client_answer_id uuid NOT NULL
  UNIQUE (participant_id, question_index); UNIQUE (participant_id, client_answer_id)
  INDEX (session_id, question_index)
```

- Формат `questions_snapshot`: `[{ index, type, text, imageUrlKey, timeLimitSec, options: [{ position, text, isCorrect }] }]`. Правильные варианты из снимка **никогда** не отдаются клиенту до `reveal`.
- RLS: учитель видит только свои тесты и сессии; ученик видит только сессии, в которых он участник, и только свои ответы. Аналогично существующим политикам (миграция 0002).
- Журнал аудита: создание и запуск сессии, выгон участника, досрочное завершение.
- Удаление данных ученика («Мои данные») распространяется на `battle_participants` и `battle_answers`. Результаты в чужой истории обезличиваются как «Участник».

## 4. API

Общие правила — как в SPEC 6.1: Zod-валидация, ошибки `{ code, message }`, CSRF для изменяющих запросов, OpenAPI обновляется.

Доступ: чужая сессия или сессия, где ученик не участник, → 404.

## 5. События реального времени (SSE)

Формат: `id: {sessionVersion}-{seq}`, `event: <тип>`, `data: <JSON>`. Каждые 15 с отправляется комментарий-heartbeat `: ping`. При подключении первым приходит событие `snapshot`.

| Событие | Кому | Данные |
|---|---|---|
| `snapshot` | всем при подключении и переподключении | Полное состояние для роли (как API-BTL-21/41) + `serverNow` |
| `participant_joined` / `participant_left` / `participant_kicked` | ведущему — с именем; ученикам — только счётчик `participantsCount` | `{ participant?, participantsCount }` |
| `question_started` | всем | `{ version, index, total, type, text, imageUrl?, options: [{position, text}], startedAt, deadlineAt, serverNow }` |
| `answer_progress` | ведущему (не чаще 1 раза в 250 мс) | `{ answered, active }` |
| `answer_accepted` | только ответившему ученику | `{ index }` |
| `question_revealed` | всем | ведущему: `{ correctPosition, distribution: [{position,count}], avgResponseMs }`; ученику: `{ correctPosition, myPosition, isCorrect, myCorrectCount, myRank, participantsCount }` |
| `leaderboard` | всем | `{ top: [{rank, displayName, correctCount}] (5), me?: {rank, correctCount} }` |
| `finished` | всем | `{ podium, table (ведущему — все; ученику — все места с именами), me }` |
| `cancelled` | всем | `{ reason }` |
| `kicked` | выгнанному | `{}` — клиент закрывает поток и показывает сообщение |

- Клиент вычисляет оставшееся время как `deadlineAt − (Date.now() + (serverNow − clientNowAtReceipt))`, то есть с поправкой на расхождение часов.
- При обрыве клиент переподключается с нарастающей задержкой (1, 2, 4, 8 с, максимум 10 с) и получает `snapshot`. После 3 неудачных попыток показывается баннер «Нет соединения, переподключаемся…».
- Для режима «Экономия трафика» никаких отличий в данных нет: события и так малы.

## 6. Серверная реализация

### 6.1 Модуль
`apps/api/src/modules/battle/`:
- `battle-quiz.controller.ts` / `.service.ts` — тесты и вопросы;
- `battle-session.controller.ts` / `.service.ts` — сессии ведущего;
- `student-battle.controller.ts` / `.service.ts` — ученик;
- `battle-engine.service.ts` — автомат состояний и переходы (единственное место, где меняется фаза);
- `battle-scoring.ts` — чистые функции рейтинга (покрыты unit-тестами);
- `battle-code.ts` — генерация и нормализация кода;
- `battle-realtime.gateway.ts` — интерфейс публикации и подписки (SSE + Redis), см. 6.4;
- `battle.dto.ts`. Схемы DTO — в `packages/shared` (как остальные).

### 6.2 Таймеры
- При `question_started` ставится отложенная задача BullMQ `battle:close-question` на `deadlineAt + 500 мс` с данными `{ sessionId, index, version }`. Нужна новая очередь `battle` в `apps/worker/src/queues.ts`.
- Автопереход (если включён) — отложенная задача `battle:auto-next`.
- Задача вызывает тот же `BattleEngine.closeQuestion(sessionId, index, version)`. Если состояние уже изменилось, операция ничего не делает.
- Досрочное закрытие (все ответили) запускается из обработчика ответа: счётчик в Redis (`INCR`) сравнивается с числом активных, затем тот же идемпотентный переход.
- Фоновая задача раз в минуту: истечение сессий (2.3) и пометка неактивных участников.

### 6.3 Ответ ученика (порядок операций)
1. Проверить участие, что ученик не выгнан, фазу `question`, `index == current_index` и `now ≤ deadline + 500 мс`.
2. Вычислить правильность по `questions_snapshot`.
3. `INSERT … ON CONFLICT DO NOTHING` в `battle_answers` (уникальность `participant_id + question_index`).
4. Если вставка прошла: `INCR` счётчика в Redis, событие `answer_progress` ведущему, `answer_accepted` ученику.
5. Если вставлено не было: тот же `clientAnswerId` → 200, другой → 409 `alreadyAnswered`.

### 6.4 Слой реального времени
- `BattleRealtime.publish(sessionId, event, audience)`, где `audience` — `host`, `students`, `participant:{id}` или `all`. Публикация идёт через Redis `PUBLISH battle:{sessionId}`.
- Каждый экземпляр API держит одну подписку `PSUBSCRIBE battle:*` и раздаёт события своим открытым SSE-соединениям по сессии и аудитории.
- Персональные данные (`question_revealed` для ученика) формируются на экземпляре, который держит соединение ученика: в Pub/Sub уходит общий payload, персонализация происходит локально по данным из Redis/PG. Так правильность чужих ответов никому не утекает.
- Соединения закрываются при `finished`/`cancelled` (через 60 с после события), при выгоне и при выходе пользователя из аккаунта.
- Лимит: не больше 2 одновременных SSE-соединений на пользователя на одну сессию; лишние закрываются (старейшее первым).

### 6.5 nginx и инфраструктура
- Для путей `…/events` убедиться: `proxy_buffering off`, `proxy_read_timeout 3600s`, заголовок `X-Accel-Buffering: no`, без gzip-буферизации. Проверить на локальном nginx из `infra/`.
- Переменные окружения не добавляются (если нужны — внести в SPEC 2.3 и `.env.example`).

### 6.6 Нагрузочные цели (проверяются в B6)
- Одна сессия: 100 участников, вопрос 10 с, все отвечают в первые 3 с. p95 «ответ → `answer_accepted`» ≤ 300 мс; p95 «закрытие → `question_revealed` у всех» ≤ 1 с; без потерянных ответов.
- 20 одновременных сессий по 40 участников на одном экземпляре API без ошибок.
- Перезапуск экземпляра API посреди вопроса: все клиенты переподключились за ≤ 10 с, ответы не потеряны, игра продолжилась.

## 8. Права доступа и безопасность

- Тесты и сессии видит и меняет **только учитель-владелец** (404 для остальных). Служебные роли — по матрице 1.2 (по умолчанию нет доступа).
- Ученик входит, только если он активный участник класса сессии (BR-BTL-02). ⚠ вопрос 1.
- Правильные ответы не покидают сервер до `reveal`; проверка e2e: в сетевых ответах ученика до раскрытия нет `isCorrect` и `correctPosition`.
- Rate-limit: ввод кода (2.3), ответы — не больше 1 запроса в 200 мс на участника, потоки — 2 на пользователя.
- Все изменяющие запросы — с CSRF. SSE — только с cookie-сессией.
- Картинки вопросов — только из нашего хранилища, по подписанным ссылкам на 10 минут (BR-FILE-04).
- Журнал аудита — раздел 3.
