# OPTIMIZATION_TZ — оптимизация проекта и сайта Syntara

Версия 1 · 2026-10-26 · Исполнитель: Claude Code · Выполнять буквально; где неясно — `TODO(OWNER)` и вопрос в отчёте.
Идентификаторы: `OPT-*` (задачи), `AC-OPT-*` (приёмка). Итоговые правила (бюджеты, запреты) перенести в `docs/SPEC.md` (раздел НФТ / REQ-NFR-PERF) с записью в журнал 16; ход работы — в `docs/PLAN.md` («Оптимизация»).

## 0. Цели

1. **Диск и репозиторий.** Сократить место, которое занимает проект на компьютере разработчика и в git, не потеряв ничего нужного.
2. **Скорость сайта для пользователей.** Особенно для учеников на слабом интернете и недорогих телефонах (ключевая аудитория — школы Казахстана, в том числе сельские).
3. **Зависимости.** Убрать неиспользуемые и дублирующиеся библиотеки: меньше вес, меньше уязвимостей, быстрее установка и CI.

## 2. Что трогать НЕЛЬЗЯ (во всех этапах)

1. **Эталонные изображения:** `docs/media/image*.jpg|jpeg`, `docs/media/student-auth*.png`, `docs/media/ux/*-ref.png`, `docs/media/ux/UX-10-mobile-nav-ref.png`, `docs/media/public/`, а также **любой файл, на который ссылаются** `docs/SPEC.md`, `docs/PLAN.md`, `docs/*_TZ.md`, `docs/UX_AUDIT.md`, `CLAUDE.md` (проверить поиском путей).
2. **Учебный контент** `content/` и его иллюстрации.
3. **История git** — не переписывать (`filter-repo`, `rebase` по истории, force-push запрещены).
4. **Тома Docker с данными** (postgres, minio) — не удалять.
5. **Секреты** (`.env`) — не читать в отчёт, не выводить, не коммитить.
6. **Функциональность сайта** — всё должно работать как раньше; логику не менять.
7. Правила безопасности файлов (ClamAV, запрет макросов и таблиц), доступность, `prefers-reduced-motion` и «Экономию трафика» не ослаблять.

## 4. Аудит: генерируемые файлы и кеши (OPT-01)

Измерить и перечислить: `apps/web/.next`, `apps/web/.next-e2e`, `.turbo` (во всех пакетах), `*.tsbuildinfo`, `test-results`, `playwright-report`, `coverage`, `dist`/`build` пакетов, логи.

Для каждого: размер; кто создаёт; в `.gitignore` ли; как восстанавливается (`pnpm dev`, `pnpm build`, `pnpm e2e`); безопасно ли удалять.

Рекомендация на O2: команда `pnpm clean` (скрипт в `package.json`), удаляющая все генерируемые папки, и `pnpm clean:deep` (+ `node_modules` с последующим `pnpm install`). Проверить, что `.next-e2e` не накапливает старые сборки.

## 5. Аудит: зависимости (OPT-02)

1. Размер `node_modules`; топ-20 самых тяжёлых пакетов (с путями, кто их тянет: `pnpm why`).
2. **Неиспользуемые зависимости** в каждом `package.json` (`knip` или `depcheck`; результаты перепроверить вручную — инструменты ошибаются с динамическими импортами, конфигами и CLI).
3. **Дубли:** одна библиотека в нескольких версиях (`pnpm list --depth Infinity` / `pnpm dedupe --check`).
4. Пакеты, которые можно заменить более лёгкими без изменения поведения — только предложение, с оценкой выигрыша.
5. Отдельно — `devDependencies`, попавшие в `dependencies`, и наоборот.
6. Известные уязвимости (`pnpm audit --prod`) — для информации.

Правило O2: удаляется только одобренное; после — `pnpm install`, `pnpm dedupe`, lint, typecheck, все тесты, зелёный CI.

## 6. Аудит: файлы в git (OPT-03)

1. Топ-30 самых больших файлов в текущем дереве (`git ls-files` + размеры).
2. `docs/media` по папкам: число файлов, размер, формат, разрешение.
3. Классификация каждого скриншота:
   - **эталон** (раздел 2) — не трогать;
   - **актуальный результат** (последняя версия экрана, на который ссылается отчёт или документ) — оставить, можно сжать;
   - **устаревший рабочий** (промежуточные «до/после» прошлых итераций, перекрытые более новыми) — кандидат на удаление.
4. Предложение на O3:
   - сжатие PNG без видимой потери (oxipng / lossless) или перевод в WebP (quality ≈ 85) — с проверкой, что ссылки в документах обновлены;
   - максимальная ширина скриншотов 1600 px;
   - удаление устаревших рабочих — только по списку, одобренному владельцем.
5. **Правило на будущее** (записать в CLAUDE.md после одобрения): новые скриншоты отчётов — WebP, ширина ≤ 1600 px; промежуточные снимки не коммитить, коммитить только итоговые.
6. `.git`: размер и крупнейшие объекты в истории — **только для информации**. Не переписывать. Если владелец когда-нибудь захочет уменьшить историю — отдельная задача с резервной копией.

## 7. Аудит: Docker (OPT-04)

1. `docker system df -v` — образы, контейнеры, тома, кеш сборки; что относится к проекту.
2. Предложение: удаление висячих (dangling) образов и кеша сборки, остановленных старых контейнеров. **Тома с данными (postgres, minio) — не трогать**, том ClamAV — по согласованию (базы сигнатур скачиваются заново долго).
3. Оценка: ограничение памяти ClamAV и других сервисов в `docker-compose.yml` для разработки (если сейчас без ограничений) — только предложение.

## 8. Аудит и улучшение скорости сайта (OPT-05)

**Как мерить.** Только в **production-сборке** (`pnpm build` + start), не в режиме разработки. Сеть: эмуляция «Slow 4G» и «Fast 3G»; устройство: средний телефон (Lighthouse mobile). Страницы:
- гость: главная, «Предметы», «О проекте», урок базового предмета;
- ученик: каталог, «Мой класс», урок («Обзор» и «Квиз»), «Показатели», «Достижения», Battle (лобби и вопрос), профиль;
- учитель: «Мои курсы», редактор темы, «Аналитика класса», «Карта освоения», экран ведущего Battle.

**Что измерить по каждой странице:**
- JS первой загрузки (сжатый) — бюджет SPEC ≤ 500 КБ;
- CSS, шрифты, изображения (вес, формат, размеры);
- Lighthouse mobile: Performance, LCP, CLS, TBT/INP;
- число запросов к API при открытии и их время (p50/p95 по логам/метрикам);
- самые медленные SQL-запросы (pg_stat_statements или логирование > 200 мс) и отсутствующие индексы — только анализ.

**Карта бандла:** `@next/bundle-analyzer` — крупнейшие модули по страницам; что попало в общий чанк без необходимости.

**Типовые улучшения, которые нужно оценить (предложить с ожидаемым выигрышем; делать на O4 только одобренное):**
1. Тяжёлые части интерфейса — ленивой загрузкой (`dynamic import`): редактор Markdown, диаграммы аналитики, Battle ведущего, календарь активности, модальные окна.
2. Иконки — импорт по одной, не целиком (проверить tree-shaking `lucide-react`).
3. Шрифты — `next/font`, только нужные начертания и наборы символов (кириллица, казахские символы, латиница), `font-display: swap`.
4. Изображения — `next/image` или эквивалент: правильные `width/height` (без сдвигов, CLS), `loading="lazy"` ниже первого экрана, WebP/AVIF, адаптивные размеры. Иллюстрации уроков и аватары — в разумном разрешении.
5. Серверные компоненты и кеширование: страницы «обложки» и базовые уроки — статическая генерация или кеш с ревалидацией, если сейчас рендерятся на каждый запрос без необходимости.
6. HTTP: сжатие (gzip/brotli) и кеширование статики в nginx (`Cache-Control: immutable` для файлов с хешем).
7. API: лишние повторные запросы на клиенте (дубли, отсутствие кеша TanStack Query), запросы «N+1», недостающие индексы.
8. «Экономия трафика»: убедиться, что в этом режиме действительно не грузятся декоративные элементы, крупные картинки и периодические запросы.

**Целевые показатели (после O4, production, Lighthouse mobile):**
| Показатель | Цель |
|---|---|
| JS первой загрузки | ≤ 500 КБ (бюджет SPEC); для страниц «обложки» и урока — стремиться к ≤ 300 КБ |
| Lighthouse Performance | ≥ 85 для страниц гостя и урока |
| LCP (Slow 4G) | ≤ 2,5 с |
| CLS | ≤ 0,1 |
| p95 API для основных экранов | ≤ 300 мс (локально) |

Если цель недостижима без изменения функциональности — указать причину и предложить вариант.

## 9. Защита от возврата (OPT-06, этап O5)

1. В CI — проверка бюджета JS первой загрузки по страницам (сборка падает при превышении 500 КБ).
2. В CI — проверка, что в git не попадают генерируемые папки и файлы больше 1 МБ (кроме разрешённых эталонов — список исключений).
3. `pnpm clean` и `pnpm clean:deep` описаны в `START.md` / README.
4. Правила для скриншотов (раздел 6.5) — в `CLAUDE.md`.
5. Периодическая проверка неиспользуемых зависимостей (`knip`) — отдельной командой `pnpm deps:check`.
